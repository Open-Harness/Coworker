# Audit, 26 November 2026: where Co-worker stands

Tested by hand on `pnpm dev` (the fake world), read against `docs/book.md` and `docs/github-plan.md`, and checked against real models.

## What was expected

- **The engine is pi-durable.** One Harness. A piece of work is a durable run, and its threads are forks. Tools are pi-durable tools: read, write, edit and bash go through `boxes.env(work)` as an ExecutionEnv. A wait is a parked tool with a signal and a deadline. Every tool call is a durable, traced task. Book: "Kept as machinery, rebuilt around agent-engine (pi-durable, how a turn runs)".
- **Every model call goes through pi-ai,** so Anthropic, OpenAI and Google each speak their own format natively. Never a raw call.
- **Replaced means removed.** The old manager (3,472 lines) goes when the new one is there. It does not run beside it.
- **The score is not the product.** Each slice is used by hand (`pnpm dev`) beside its drawings before it counts.
- **It is built so the core can later move onto Orthograph** as one seam.

## What was built

- **Two hand-written loops run the live paths.** Juno's chat runs `console` → `turns/internal/run.ts` (at most 40 calls). A manager's work runs in `working/internal/thread.ts` (at most 80 calls).
- **Model calls are a raw `fetch`** to `/chat/completions` (`completion/internal/ask.ts:77`).
- **pi-durable is imported in 66 files, almost all in the old layer** the plan said to replace: `manager` (3,472 lines), `chat-host` (1,446) and `agent-engine`. The new layer uses none of it: `working` (2,462), `turns`, `completion` and `console` (4,726).
- **Both generations are deployed:** five Durable Object classes. Directory and Workspace (v1), WorkspaceObject and ManagerObject (v2), and ManagerStore (v5).
- **Size:** 88 modules and 92,567 lines.

## Real models (the jobs)

- **Before the push fix:** 8 of 18 passed. **After it (`fe491b5`):** 14 of 18.
- **The 4 left timed out** (at 6 and 12 minutes). All 240 model calls returned 200, so the stall is inside the product, and nothing records where.
- **Spent:** $18.24 of the $50 cap.

## Why 100 of 100 hid this

1. **The flows start from a back door.** They add a model through `POST /api/workspaces/:id/models`, not through the screens. So no eval ever set up a workspace the way a person does.
2. **Screen evals compare against the drawings.** A button that only shows a toast looks right, so it passes.
3. **The scripted models speak OpenAI's format,** so the Anthropic path never ran.
4. **The jobs are not in the score.** They are the only real-model evals.
5. **The evals check behaviour, not how it is built.** Two loops, and no pi-durable in the live path, are invisible to them.
6. **The hand check never happened.** The book asks for `pnpm dev` on every slice, and the app could not start from a clone.

## What is worth keeping

- **Auth:** better-auth with mail links. The D1 control plane, making a workspace, and persistence.
- **The models backend:** it connects keys, checks them and lists models, when something calls it.
- **The vault.**
- **The screens:** drawn and rendered on the design system. They need wiring, not redrawing.
- **The eval world:** fake GitHub, fake mail, scripted models, and flows that run in workerd. This is the most valuable part.
- **The module shape is mostly obeyed.** No module imports another's `internal/`, only one file is over 250 lines (a generated one), and 6 modules have no tests. But many files sit at 244 to 249 lines: they were trimmed to pass the check, not shaped to read well.

## What is wrong

1. **The engine is not pi-durable.** This is the core.
2. **Model calls do not go through pi-ai,** so Anthropic, the provider most people will bring, does not work.
3. **Two generations are live:** five Durable Objects, and the old manager, chat-host and manager-store.
4. **The screens are not wired.** Setup drops answers, six buttons only show a toast, and the palette has a broken link.
5. **Deployed, a manager cannot run a command or push.**
6. **Nothing is observable.** There are no traces, so a stall cannot be found.
7. **It cannot be started from a clone** without steps nobody wrote down.
8. **The evals enter through back doors**, not the way a person does.

## The call

Keep the shell, rebuild the core. Burning everything down would throw away the parts that work and that took the longest: auth, the control plane, the screens and, above all, the eval world. Patching in place keeps the hand-written loops, the thing you said you would never have agreed to.

In order:

1. **One engine on pi-durable,** with model calls through pi-ai and Cloudflare traces from day one.
2. **Delete both generations of engine and their Durable Objects.**
3. **Wire the screens to real actions.**
4. **Make the evals enter the way a person does:** setup through the screens, an Anthropic-format scripted model, and the jobs counted in the score.

## Done the same day: the core is out, the shapes are in

Step 2 of the call is done, on branch `core`. Step 1 has its shapes and nothing behind them.

**What was removed.** Both generations of engine and everything that only they used:

- the prototype's chat (`directory`, `chat-host`, `app`, the `_app` routes, the chat half of `ui`);
- the first product's manager (`manager`, `brain`, `agent-engine`, `turns`, `completion`, `transcript`, `board` and the rest), with its HTTP routes (managers, home, search, a manager's settings) and its flows;
- the hand-written loop inside `working` (its `internal/`), and `setting-up`.

The Durable Object classes `Directory`, `Workspace` and `ManagerObject` are gone from the code, and the `v6` migration in `wrangler.jsonc` deletes them on the next deploy, with their data.

**What stayed.** The shell (auth, the control plane, the workspace object, the vault, the screens, the console), the pure modules (`work`, `threads`, `playbook`, `boxes`, `models`, `github`, `intake`, `deciding`), the manager's own object (`manager-store`: its playbook and versions), and the eval world. `pnpm check` is green: typecheck, lint, format, shape, size, UI, and 290 tests (34 todo). The app builds. Signed in, the home page loads, and a chat answers "I could not answer: the agent loop is not built yet (agent.answer)."

**The new shapes.**

- **`agent`:** the loop seam. One pi-durable Harness in each manager's object. `open`, `tell`, `signal`, `stop` and `lines` cover threads on work. `answer`, `fork` and `ask` cover a conversation with a person and a single model call. `wake` and `resume` cover the alarm. Errors come back as values: `NotBuilt`, `NoModel`, `ModelFailed`, `OverBudget`, `OutOfTurns`, `BoxDenied`, `Interrupted`, `StorageFailed`. Every call answers `NotBuilt` until it is built. Tools are `AppTool`s, and each run is given the pi-durable call id so an outside effect happens once.
- **`telemetry`:** the span seam that the Harness's `telemetry` option is fed from, for Cloudflare Workers Observability.
- **`models.PiModels`:** the pi-ai model registry the loop asks for.

Every model call now goes through `agent.answer` or `agent.ask`: the chat, the weekly look, comments, the judge and its trials. Transcripts belong to the loop: the console no longer stores messages, and a chat is forked by `agent.fork`.

**What is red because the core is not built.** These answer that they are not built, and do not fail silently:

- chat, comments and the weekly look;
- the judge of what comes in, so items wait;
- setting up from a sentence (a set-up already kept can still be read);
- forking a chat;
- a manager's threads.

An approval of a first-product button is recorded as failed, with the reason. A Trigger for a first-product manager is dropped, with the reason. Usage shows no runs.

**Still open before building, with the Orthograph goal.** Orthograph's design puts one Durable Object per run. This plan puts one Harness per manager's object, with threads as forks. See `src/modules/agent/README.md`.
